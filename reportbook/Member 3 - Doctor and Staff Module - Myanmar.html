Where this module sits · ဤ Module ၏ စနစ်အတွင်း တည်နေရာနှင့် အခန်းကဏ္ဍ
The Smart Queue Engine (Member 2 — rule/QueueRule, DoctorAvailabilityRule, EmergencyRule) decides queue order. This module is the two portals that actually act on that order: the doctor pulling patients out of it one at a time, and staff sitting at the front desk keeping emergency cases honest before they jump the line. Neither portal touches the database directly — both call QueueService, which is the single place queue state actually changes.
[မြန်မာပြန်] Smart Queue Engine (Member 2 မှ QueueRule, DoctorAvailabilityRule, EmergencyRule) သည် လူနာများ စောင့်ဆိုင်းရမည့် အစီအစဉ် (Queue Order) ကို ဆုံးဖြတ်ပေးသည်။ ဤ Member 3 Module သည် ထိုစီထားသော Queue အပေါ် အမှန်တကယ် လက်တွေ့အသုံးချ လှုပ်ရှားပေးသည့် Portal (၂) ခု ဖြစ်သည် — (၁) ဆရာဝန်သည် Queue ထဲမှ လူနာများကို တစ်ဦးချင်းစီ ခေါ်ယူကုသပေးခြင်း (Doctor Portal)၊ (၂) ဧည့်ကြိုကောင်တာရှိ ဝန်ထမ်းများသည် အရေးပေါ်လူနာများ ကျော်တက်လာချိန်တွင် အစစ်အမှန် ဟုတ်/မဟုတ် စစ်ဆေးအတည်ပြုပေးခြင်း (Staff Portal)။ Portal နှစ်ခုစလုံးသည် Database ကို တိုက်ရိုက် Access မလုပ်ဘဲ QueueService ကိုသာ လှမ်းခေါ်ပြီး Queue ၏ State ပြောင်းလဲမှုအားလုံးကို QueueService တစ်ခုတည်းကသာ တာဝန်ယူဆောင်ရွက်ပါသည်။
Queue state machine · Queue အဆင့်ဆင့် ပြောင်းလဲမှု State Machine Queue.java
Every queue entry is a row moving left to right through these states. Doctor actions drive the top row; PAUSED lets a doctor step away without losing the patient's place; the bottom row are the ways a queue entry can end without being served.
(လူနာမှတ်တမ်းတိုင်းသည် ဘယ်မှညာသို့ အောက်ပါ State များအတိုင်း ကူးပြောင်းသည်။ အပေါ်တန်းသည် ဆရာဝန်၏ ကုသမှုစီးဆင်းပုံဖြစ်ပြီး PAUSED သည် ခေတ္တထွက်ခွာချိန် လူနာ့အလှည့် မပျောက်စေရန် ထိန်းပေးသည်။ အောက်တန်းသည် ဆေးမကုသရသေးဘဲ စာရင်းပြီးဆုံးသွားနိုင်သည့် နည်းလမ်းများ ဖြစ်သည်။)

if (currentConsultation(doctorId) != null)
    throw new IllegalStateException("Finish or start the current consultation first.");

// ၂။ ဤဆရာဝန်ထံ စောင့်ဆိုင်းနေသော WAITING လူနာအားလုံးကို ဆွဲထုတ်သည်
List<Queue> waiting = queueRepository.findWaitingQueuesByDoctor(doctorId);
if (waiting.isEmpty()) return null;

// ၃။ EmergencyRule ဖြင့် ဦးစားပေးအဆင့် အမြင့်ဆုံးလူနာကို ရှေ့ဆုံးသို့ ရွေးထုတ်သည်:
//    EMERGENCY > APPOINTMENT > NORMAL၊ ဦးစားပေးတူပါက ရောက်ရှိသည့် မူလနံပါတ်အတိုင်း (FIFO)
Queue next = emergencyRule.reorderByPriority(waiting).get(0);
queueRepository.callNext(next.getQueueId());   // WAITING -> CALLED
notificationService.notify(next.getPatientId(), "It's your turn! ...");

// ၄။ နောက်တွင် ကျန်ရှိနေသော စောင့်ဆိုင်းလူနာ အားလုံးအတွက် ခန့်မှန်းစောင့်ဆိုင်းချိန်ကို Batch UPDATE ဖြင့် ပြန်တွက်သည်
updateRemainingWaitTimes(doctorId);
RULE/EMERGENCYRULE.JAVA — THE ACTUAL SORT (အမှန်တကယ် ဦးစားပေး စီပေးပုံ)
waitingQueues.sort((q1, q2) -> {
    int p1 = priorityRank(q1), p2 = priorityRank(q2);   // EMERGENCY=1, APPOINTMENT=2, NORMAL=3
    if (p1 != p2) return Integer.compare(p1, p2);
    return Integer.compare(q1.getPosition(), q2.getPosition()); // ဦးစားပေးတူပါက မူလရောက်သည့်အစဉ်အတိုင်း (FIFO)
});

အကြောင်းပြချက် ရှင်းလင်းချက်: priorityRank() သည် queue ၏ priority field တစ်ခုတည်းကိုသာ ကြည့်ပြီး sort စီတာ ဖြစ်သည်။ လူနာ (သို့မဟုတ် staff) က emergency ဟု သတ်မှတ်လိုက်သည်နှင့် ၎င်း၏ priority သည် "EMERGENCY" ဖြစ်သွားသည့်အတွက် emergencyConfirmed ဖြစ်မဖြစ် အပေါ် မမူတည်ဘဲ တန်းစီဇယား ရှေ့ဆုံးသို့ ချက်ချင်း ရောက်သွားပါသည်။ Staff confirmation သည် queue အစီအစဉ်ကို ထိန်းချုပ်တာ မဟုတ်ဘဲ၊ ကောင်တာဝန်ထမ်းက အမှုတွဲ အစစ်အမှန် ဟုတ်/မဟုတ် စစ်ဆေးပြီး မည်သူကိုင်တွယ်သည်ကို Formally Log မှတ်တမ်းတင်ပေးခြင်း ဖြစ်သည်။ လူနာ့အသက်အန္တရာယ် ဘေးကင်းရေးအတွက် စနစ်က အလိုအလျောက် Fast-track ဦးစားပေးထားပြီး ဖြစ်သည်။ အကယ်၍ "အရေးပေါ်အမှား (False Alarm)" ဖြစ်ခဲ့လျှင် မည်သို့လုပ်မည်နည်းဟု မေးပါက Reject လုပ်လိုက်ရုံဖြစ်သည် — စာရင်းကို အဆင့်နှိမ့်ချခြင်း (Demote) မျိုးမဟုတ်ဘဲ Queue မှတ်တမ်းကို လုံးဝ ပယ်ဖျက် (Cancelled Outright) ပစ်လိုက်ခြင်း ဖြစ်သည်။

Likely questions · မေးလေ့ရှိသော မေးခွန်းများနှင့် အကောင်းဆုံး ဖြေဆိုချက်များ
၁။ Why can't a doctor call a second patient while one is already called?
(ဆရာဝန်တစ်ဦးသည် လူနာတစ်ဦးအား Call ထားစဉ် ဒုတိယလူနာအား အဘယ်ကြောင့် ထပ်ခေါ်၍ မရသနည်း?)
callNext() checks currentConsultation() first, which is CALLED-or-SERVING — one active consultation per doctor at a time, enforced server-side (not just the disabled button).
[မြန်မာလို ဖြေရန်] callNext() method သည် ဦးစွာ currentConsultation() ကို စစ်ဆေးပါသည်။ ၎င်းသည် CALLED သို့မဟုတ် SERVING အခြေအနေရှိ လူနာရှိမရှိ စစ်ဆေးခြင်းဖြစ်ပြီး၊ ဆရာဝန်တစ်ဦးလျှင် အချိန်တစ်ခုတွင် active consultation တစ်ခုသာ လက်ခံနိုင်စေရန် Backend Server-side တွင် တင်းကျပ်စွာ စစ်ဆေးထားသောကြောင့် ဖြစ်ပါသည် (UI ပေါ်ရှိ disabled ခလုတ်တစ်ခုတည်းဖြင့်သာ ကာကွယ်ထားခြင်း မဟုတ်ပါ)။
၂။ What happens to wait-time estimates when a patient completes?
(လူနာတစ်ဦး ကုသမှုပြီးမြောက် (Complete) သွားသောအခါ စောင့်ဆိုင်းချိန် ခန့်မှန်းချက်များ ဘာဖြစ်သွားသနည်း?)
completeCurrent() calls updateRemainingWaitTimes(), which recomputes every remaining WAITING patient's estimate as position × avg consultation minutes (plus a lunch-break offset) and writes them all in one batched UPDATE.
[မြန်မာလို ဖြေရန်] completeCurrent() သည် updateRemainingWaitTimes() ကို လှမ်းခေါ်ပါသည်။ ၎င်းသည် ကျန်ရှိနေသော WAITING လူနာတိုင်း၏ ခန့်မှန်းချိန်ကို (စောင့်ဆိုင်းအလှည့်နံပါတ် × ပျမ်းမျှ ကုသချိန်မိနစ်) ဖြင့် တွက်ချက်ကာ (နေ့လယ်စာစားချိန် အနားယူချိန်များပါ ထည့်သွင်းတွက်ချက်ပြီး) တစ်ကြိမ်တည်းသော Batched UPDATE ဖြင့် Database တွင် အားလုံးကို ပြိုင်တူ အပ်ဒိတ်လုပ်ပေးပါသည်။
၃။ Can staff move a patient to a different doctor?
(Staff ဘက်မှ လူနာအား အခြားဆရာဝန်ထံသို့ ပြောင်းရွှေ့ပေးနိုင်ပါသလား?)
Yes — /api/staff/queues/reassignable lists candidates, /api/staff/queues/{id}/reassign moves one queue entry to a different doctorId via QueueService.reassignDoctor.
[မြန်မာလို ဖြေရန်] ရပါသည် — /api/staff/queues/reassignable မှတစ်ဆင့် ပြောင်းရွှေ့နိုင်သော လူနာများကို ရယူနိုင်ပြီး၊ /api/staff/queues/{id}/reassign မှတစ်ဆင့် QueueService.reassignDoctor ကို အသုံးပြုကာ သက်ဆိုင်ရာ doctorId အသစ်ထံသို့ တိုက်ရိုက် လွှဲပြောင်းပေးနိုင်ပါသည်။
၄။ How does PAUSED differ from just not calling the next patient?
(PAUSED အခြေအနေသည် နောက်လူနာအား မခေါ်ဘဲ ထားခြင်းနှင့် အဘယ်သို့ ကွာခြားသနည်း?)
PAUSED is specifically for a patient already SERVING — the doctor steps away mid-consultation without marking it COMPLETED. resume() puts them back to SERVING; the queue slot isn't given up.
[မြန်မာလို ဖြေရန်] PAUSED သည် ကုသမှု စတင်နေဆဲ (SERVING) ဖြစ်နေသော လူနာအတွက် သီးသန့်ဖြစ်ပါသည်။ ဆရာဝန်သည် ကုသမှုမပြီးသေးဘဲ ခေတ္တ အရေးပေါ် ထွက်ခွာရချိန်တွင် လူနာအား COMPLETED မလုပ်ဘဲ PAUSED လုပ်ထားခြင်း ဖြစ်သည်။ ပြန်ရောက်လာပါက resume() ဖြင့် SERVING သို့ ပြန်ပြောင်းနိုင်ပြီး လူနာ၏ Queue အလှည့်အကွက် မပျောက်ပျက်စေပါ။

"ဆက်လက်ပြီး ဧည့်ကြိုကောင်တာဖြစ်တဲ့ Staff Portal ရဲ့ Emergency Cases စာမျက်နှာကို ပြသပါမယ်။ ဒီနေရာမှာ Pending ဖြစ်နေတဲ့ အရေးပေါ်လူနာတွေနဲ့ အနီရောင် Critical Cases Banner ကို တွေ့ရပါမယ်။ ကျွန်မ အရေးပေါ်လူနာတစ်ဦးကို 'Confirm' လုပ်လိုက်ပါမယ်။ ဒီနေရာမှာ အရေးကြီးတဲ့ အချက်ကတော့ — ဒီလူနာဟာ စနစ်ထဲကို Emergency လို့ စာရင်းသွင်းလိုက်ကတည်းက Queue ရဲ့ ရှေ့ဆုံးကို ရောက်နှင့်နေပြီးသား ဖြစ်ပါတယ်။ Staff က Confirm လုပ်တာဟာ Queue ကို ထပ်ပြီး Re-sort စီတာ မဟုတ်ဘဲ၊ ကောင်တာဝန်ထမ်းက လူနာရဲ့ အရေးပေါ်အခြေအနေ အစစ်အမှန်ဖြစ်ကြောင်း အတည်ပြုပြီး ဘယ်သူကိုင်တွယ်သလဲဆိုတာ တာဝန်ခံ လက်မှတ်ထိုး Log မှတ်တမ်းတင်ပေးခြင်း ဖြစ်ပါတယ်ရှင့်။ အကယ်၍ အရေးပေါ်အမှားဖြစ်ရင်တော့ Reject လုပ်ပြီး တန်းစီဇယားကနေ လုံးဝ Cancel ဖျက်ပစ်နိုင်ပါတယ်ရှင့်။"
Architecture & Frontend-Backend Contract · စနစ်တည်ဆောက်ပုံနှင့် ချိတ်ဆက်ပုံ အဓိကအချက်များ
Backend Enforcement (Java Spring Boot)
  • Single Source of Truth: Queue ၏ အခြေအနေပြောင်းလဲမှု မှန်သမျှသည် QueueService.java တစ်ခုတည်းတွင်သာ ဖြစ်ပေါ်သည်။
  • Strict Invariant: ဆရာဝန်တစ်ဦးလျှင် အချိန်တစ်ခုတွင် active consultation (CALLED သို့မဟုတ် SERVING) တစ်ဦးသာ ရှိစေရန် Controller နှင့် Service အဆင့်တွင် စစ်ဆေးသည်။
  • Batched Performance: လူနာတစ်ဦး Complete ဖြစ်တိုင်း စောင့်ဆိုင်းလူနာအားလုံး၏ wait time ကို SQL Batch Update ဖြင့် တစ်ပြိုင်နက် သိမ်းဆည်းသည်။
Frontend Experience (React / Vite)
  • Lightweight Polling: doctor.queue.tsx သည် ၈ စက္ကန့်တစ်ကြိမ် လိုအပ်သော data သာပါသည့် ပေါ့ပါးသော API ကို ခေါ်ယူသည်။
  • Button State Mirroring: Active consultation ရှိနေချိန်တွင် Call Next ခလုတ်အား UI ပေါ်တွင် disable လုပ်ထားသဖြင့် API Reject မဖြစ်စေရန် ကြိုတင်ကာကွယ်သည်။
  • Optimistic Updates: staff.emergency.tsx တွင် Confirm/Reject နှိပ်ပါက စာရင်းတစ်ခုလုံး အသစ်ပြန်မခေါ်ဘဲ Local State ကို ချက်ချင်း အပ်ဒိတ်လုပ်သည်။
Flagship Flow: Step-by-Step Execution Lifecycle · အဆင့် ၄ ဆင့်ဖြင့် လည်ပတ်ပုံ
၁။ Validation: currentConsultation(doctorId) != null စစ်ဆေးပြီး ရှိနေပါက IllegalStateException ထုတ်ကာ နောက်လူနာ ထပ်ခေါ်ခွင့် ငြင်းပယ်သည်။
၂။ Fetching: သက်ဆိုင်ရာ ဆရာဝန်ထံ တန်းစီစောင့်ဆိုင်းနေသော WAITING လူနာများအားလုံးကို ဆွဲထုတ်သည်။
၃။ Sorting & Notification: emergencyRule.reorderByPriority() ဖြင့် ဦးစားပေးအဆင့် (EMERGENCY=1, APPOINTMENT=2, NORMAL=3) အလိုက် စီပြီး ရှေ့ဆုံးလူနာအား CALLED အဖြစ် ပြောင်းကာ လူနာထံ Notification ပေးပို့သည်။
၄။ Wait-Time Recomputation: ကျန်ရှိသော စောင့်ဆိုင်းလူနာအားလုံးအတွက် စောင့်ဆိုင်းချိန်အား ချက်ချင်း ပြန်လည်တွက်ချက်ကာ Database တွင် အစုလိုက် သိမ်းဆည်းသည်။

EXAMINATION & VIVA DEFENSE MASTER STRATEGY
မေးခွန်းများအား အမှတ်ပြည့်ရစေမည့် နှုတ်ဖြေနည်းဗျူဟာများ
ဆရာ/ဆရာမများ၏ မေးခွန်းများအား အထူးယုံကြည်မှုရှိရှိ ဖြေဆိုနိုင်ရန် လမ်းညွှန်ချက်
စာမေးပွဲတွင် ဆရာ/ဆရာမများသည် သင်၏ Code နှင့် Architecture ကို အမှန်တကယ် နားလည်သဘောပေါက်မှု ရှိ/မရှိ စစ်ဆေးလေ့ရှိပါသည်။ အောက်ပါ မေးခွန်းနှင့် ဖြေဆိုပုံ နည်းဗျူဟာများကို ကြိုတင်လေ့ကျင့်ထားပါ။
မေးခွန်း ၁: "DoctorApiController ထဲက Dashboard Endpoint နဲ့ Queue Endpoint က ဘာကွာခြားလို့ နှစ်ခု ခွဲထားတာလဲ?"
အကောင်းဆုံး ဖြေဆိုချက်: "ဒါက Performance Optimization ကြောင့် ဖြစ်ပါတယ် ဆရာ/ဆရာမရှင့်။ /dashboard endpoint ကတော့ ဆရာဝန် စာမျက်နှာ စတင်ဖွင့်ချိန်မှာ appointments တွေ၊ ပြီးမြောက်ခဲ့တဲ့ stats တွေအပါအဝင် အချက်အလက် အကုန်လုံးကို အပြည့်အစုံ ဆွဲယူတာ ဖြစ်ပါတယ်။ ဒါပေမဲ့ /queue endpoint ကတော့ Live Queue မျက်နှာပြင်ကနေ ၈ စက္ကန့်တစ်ကြိမ် မကြာခဏ ပုံမှန်ခေါ်ယူ (Polling) လုပ်နေတဲ့အတွက် မလိုအပ်တဲ့ appointment နဲ့ stat တွေကို ဖယ်ထုတ်ပြီး လက်ရှိ တန်းစီနေတဲ့ လူနာစာရင်း သီးသန့်ကိုသာ Database round-trip အနည်းဆုံးနဲ့ ပေါ့ပေါ့ပါးပါး ပြန်ပို့ပေးနိုင်အောင် သီးခြား ခွဲထုတ်ထားတာ ဖြစ်ပါတယ်ရှင့်။"
မေးခွန်း ၂: "လူနာတစ်ဦးဟာ တန်းစီနေရင်း ဆရာဝန်ပြောင်းချင်တယ်ဆိုရင် စနစ်က ဘယ်လို ကိုင်တွယ်သလဲ?"
အကောင်းဆုံး ဖြေဆိုချက်: "Staff Portal မှာ ပါဝင်တဲ့ /api/staff/queues/reassignable ကနေတစ်ဆင့် လက်ရှိ WAITING ဖြစ်နေတဲ့ လူနာစာရင်းကို ရယူနိုင်ပြီး၊ /api/staff/queues/{id}/reassign endpoint ကို သုံးကာ QueueService.reassignDoctor() နဲ့ အခြားဆရာဝန်ထံသို့ တိုက်ရိုက် လွှဲပြောင်းပေးနိုင်ပါတယ်။ ဒီအခါ မူလဆရာဝန်ရဲ့ စောင့်ဆိုင်းချိန်ရော ဆရာဝန်အသစ်ရဲ့ စောင့်ဆိုင်းချိန်ပါ အလိုအလျောက် ပြန်လည်တွက်ချက် ညီညွတ်သွားစေပါတယ်ရှင့်။"
မေးခွန်း ၃: "Frontend မှာ ခလုတ်ကို Disable လုပ်ထားတာ ရှိပြီးသားကို Backend Controller မှာ ဘာလို့ ထပ်စစ်နေသေးတာလဲ?"
အကောင်းဆုံး ဖြေဆိုချက်: "Frontend က Disable လုပ်ထားတာဟာ UI/UX အရ အသုံးပြုသူ အမှားမဖြစ်အောင် ကာကွယ်ပေးတဲ့ Client-side Validation သာ ဖြစ်ပါတယ်။ ဒါပေမဲ့ တကယ့် System Security နဲ့ Data Integrity အတွက် Backend Server-side မှာ မဖြစ်မနေ ထပ်မံ စစ်ဆေးရပါမယ်။ အကယ်၍ တစ်စုံတစ်ယောက်က Postman သို့မဟုတ် cURL ကနေ API ကို တိုက်ရိုက် လှမ်းခေါ်ခဲ့ရင်တောင် Backend က 'Finish or start current consultation first' ဆိုပြီး တင်းကျပ်စွာ ငြင်းပယ်နိုင်အောင် ကာကွယ်ထားခြင်း ဖြစ်ပါတယ်ရှင့်။"
မေးခွန်း ၄: "PAUSED အခြေအနေမှာ ရှိနေတဲ့ လူနာကို ဆရာဝန်က မေ့ပြီး နောက်လူနာ ထပ်ခေါ်လို့ ရနိုင်သလား?"
အကောင်းဆုံး ဖြေဆိုချက်: "လုံးဝ မရနိုင်ပါရှင့်။ callNext() စစ်ဆေးတဲ့ currentConsultation() logic မှာ PAUSED ဖြစ်နေရင်တောင် အဆိုပါ လူနာဟာ တာဝန်ခံဆရာဝန်ထံမှာ Consultation မပြီးပြတ်သေးဘဲ ဆိုင်းငံ့ထားတာဖြစ်တဲ့အတွက် နောက်ထပ် လူနာသစ် ခေါ်ယူခွင့်ကို Backend က တားမြစ်ထားပါတယ်။ အဲဒီလူနာကို Resume လုပ်ပြီး Complete ဖြစ်အောင် ကုသပြီးမှသာ နောက်လူနာကို ခေါ်ယူနိုင်မှာ ဖြစ်ပါတယ်ရှင့်။"
